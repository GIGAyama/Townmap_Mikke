# 話を聞く

この連載の強みは、作った本人が書いていることにある。機能の説明はどこにでもあるが、
「なぜその作りにしたのか」「何をあえて作らなかったのか」は、本人からしか出てこない。

だから記事を書く前に、書き手から話を聞く。聞いていないことは書かない。
ここを飛ばすと、事実は正しいのに誰が書いても同じ記事になる。

## いつ聞くか

二回に分ける。

一回目は着手のとき。三問だけ。連載番号、なぜ作ったか、誰に届けたいか。
これで読む場所と撮る場面の狙いが決まる。

二回目は撮影のあと。ここが本番。アプリを読んで、実際に操作して、
壊れているところまで踏んだあとだから、具体的なことを聞ける。
先に聞くと、質問がどうしても「どんなアプリですか」から始まってしまい、
書き手に説明の手間をかけたうえ、返ってくるのは README に書いてあることになる。

## 聞きかたの原則

**調べて分かることを聞かない。** README、コード、撮った画面を先に読む。
「この機能はどう動きますか」は書き手の時間を奪うだけ。
そのぶんを「なぜここだけ二段階にしたんですか」に使う。

**一度に一問か二問。** 返ってきた言葉を受けて、次の質問を決める。
十問まとめて投げると、答えが全部短くなる。深いところは二の矢で出てくる。

**選択肢で聞かない。** 欲しいのは書き手の言葉なので、自由に書いてもらう。
答えにくそうな問いには「たとえば」を一つだけ添える。

**意見ではなく場面を聞く。** 「こだわりはどこですか」と聞くと、抽象語が返ってくる。
「どの子の顔が浮かんでいましたか」「最後に困ったのはいつの授業でしたか」と聞くと、
そのまま記事の一行になる材料が返ってくる。

**作らなかったものを必ず聞く。** 連載でいちばん効いているのがここ。

> なお、この機能を切るボタンはあえて作りませんでした。使わせたくない場面では
> 「今日は電球はなしね」と伝えてください。必要な子が必要なときに開ける、
> という状態を守りたかったからです。

機能の説明ではこれは書けない。作った人が、迷って、決めた跡だから読める。

**言い切りを迂回して聞く。** 「効果はありましたか」と聞くと、実体験が返ってくる。
それは書けない（作者の実践記録ではないため）。
「どうなったらいいと思って作りましたか」と聞けば、書ける形で返ってくる。

**数字と固有名は、その場で確かめる。** 「二十五種類でしたっけ」。
記事に数字を書くのは、本人の口から出たか、こちらが数えたときだけ。

**短い答えを責めない。** 「特にないです」は本当に無いことも多い。
角度を変えて一度だけ聞き直し、それでも無ければ引く。無理に引き出した話は、
書いたあとで本人が「そんなに思っていない」と感じる。

**話し言葉のまま控える。** 整えるのはあとの仕事。
「なんか、待たせてるのが嫌で」は、そのまま残しておくと、あとで効く。

## 聞く項目

上から順に聞く必要はない。会話の流れで拾えたものから埋める。

- **きっかけの場面。** いつ、どの授業の、どの瞬間に「これを作ろう」と思ったか。
  → 🏫 はじめに の冒頭になる。ここが具体的だと、記事全体が具体的になる
  「作ろうと思った日のことを覚えていますか」

- **前作との違い。** 作り直しなら、前は何が駄目だったのか
  → 🏫 はじめに。連載の読者にとって記事の意味がはっきりする

- **いちばん時間をかけたところと、その理由**
  → 📱 か、追加の見出し。記事の山になる

- **作らなかったもの、やめたもの、断ったこと**
  → 追加の見出しか ✨。いちばん効く一段落になる
  「入れようとしてやめた機能はありますか」

- **迷って、いまも決めきれていないこと**
  → どこか一段落。正直さが出て、記事が広告に見えなくなる

- **どんな場面で使われたら嬉しいか。** 願望として聞く
  → ✨ 導入のメリット
  「これがうまくいったとき、教室はどうなっていると思いますか」

- **心配していること、まだ届いていない相手**
  → 🛠️ 導入手順。ここに書くと、読み手が身構えずに済む

- **名前の由来**
  → どこかに一行。読み手が覚えて帰るのはこういうところ

- **次にやりたいこと**
  → 📝 まとめ

## 聞いたことを、どう記事にするか

取材メモをそのまま並べても記事にはならない。ここからがライターの仕事になる。

**一本の線を決める。** 取材が終わったら、この記事で言うことを一文にする。
Qalc なら「鉛筆が止まった子が、手を挙げて待たなくてよくなる」。
その線に乗らない話は、面白くても落とす。全部入れると何も残らない。

**具体に降ろす。** 「使いやすくしたかった」で止めない。
それが教室で何秒の話なのか、何人の話なのかまで聞いて書く。
「待たせていた三分」まで降ろせたら、そこが記事のいちばん強い一行になる。

**山を作る。** 困っていた、作った、壁に当たった、こうして越えた。
見出しの並びは決まっているので、起伏は 📱 と、そのあとに足す2本の中で作る。

**読み手の反論を先回りする。** 「それ、紙でもできるのでは」「うちの端末では重いのでは」。
書き手に聞けば、たいてい答えを持っている。その答えを本文に置く。
先回りされた読み手は、最後まで読む。

**意外を一つ置く。** 作らなかったもの、失敗、思っていたのと違った反応。
順風満帆な話は読み飛ばされる。

**追加の見出しは、機能名ではなく効き目で書く。**
「かんがえるどうぐ機能」ではなく「💡 鉛筆が止まった子を助ける『かんがえるどうぐ』」。
note は見出しから目次を作るので、目次だけ読んで中身が分かる形にする。

**冒頭の三行で、読み手に自分の教室を思い出させる。**
最初の一段落は検索結果とSNSの説明文にもなる（110字で切られる）。

**出し惜しみしない。** 続きは次回、をやらない。この記事で全部渡す。

## 書くときの約束

- **聞いていないことを、書き手の考えとして書かない。** 事実は資料から、
  考えは取材から。どちらの裏づけも無い一文は消す
- **書き手の言葉を、一つはそのまま残す。** 整えすぎると、誰の記事か分からなくなる
- **誇張しない。** 取材で「たぶん」と言われたものは「〜だと思います」で書く
- **取材メモは `docs/note/README.md` の中に残す。** 別ファイルにしない。
  `docs/note/` に置いた Markdown は、2本目の記事として自動で拾われる
- 書き上げたら、取材メモと本文を突き合わせて、出どころのない主張を消す

## 話を聞けないとき

書き手が忙しくて答えられないことはある。むしろそちらのほうが多い。
そのときは空けずに、**書ける範囲で埋めて、あとから差し替えてもらう。**

### 埋めてよいもの

コードとコミット履歴と画面から、裏が取れる事実だけ。

- 何をしたか。「切るボタンは用意していません」「配点は15点にしてあります」
- いつ変わったか。「以前はクラウドに預けていましたが、いまは端末の中だけです」
- どう動くか。実際に操作して確かめたこと

### 埋めてはいけないもの

なぜそうしたか。コミット履歴が示すのは何をしたかであって、
どういう気持ちでそう決めたかではない。

「必要な子が必要なときに開ける、という状態を守りたかったからです」は、
本人に聞かないと書けない。似た文をこちらで作ると、本人が読んだときに
「そんなに思っていない」となり、その記事は本人の名前で出せなくなる。

書けるのは「いまはこうなっています」まで。理由の一文を足したくなったら、
そこが差し替えの場所になる。

### 差し替えやすい形で書く

**理由を一段落にまとめて置く。** 何段落にもまたいで散らすと、
あとから書き手が直すときに、記事全体を読み直すことになる。
一段落を丸ごと入れ替えれば済む形にしておけば、五分で終わる。

**記事の中に印を残さない。** `TODO` や `※要確認` を書きこむと、
翌朝の組み立てでそのまま紹介ページに出る。記事は公開される形のまま置く。

**代わりに `docs/note/README.md` に差し替え表を作る。**
どの段落を、何を聞いて、どう差し替えるか。段落の書き出しの20字を目印にする。

```
差し替え待ちのところ

1. 「切るボタンは用意していません。」で始まる段落
   聞きたいこと  この機能を切れなくしたのは、どういう考えからですか
   いまの状態    事実だけ書いてあります。理由の一文を足すと強くなります

2. 「以前はクラウドに預けていました」で始まる段落
   聞きたいこと  やめたきっかけは何でしたか
   いまの状態    経緯だけ。やめた理由が入ると、この節が記事の山になります
```

**差し替えの見返りを書く。** 「理由が入ると強くなる」と書いてあれば、
書き手は忙しくても、そこだけは埋める気になる。

### そのあと

差し替えの一文が返ってきたら、その段落だけを直して push する。
翌朝の組み直しで紹介ページに反映される。記事を書き直す必要はない。
