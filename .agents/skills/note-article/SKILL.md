# note の紹介記事を作る

リポジトリにある学校向けWebアプリについて、note の連載
「教室で使えるかもしれないもの作り」に載せる紹介記事を、実画面のスクリーンショットつきで作る。

納品物はこの3つ。

```
docs/note/
├── <app>-note-article.md   記事本文。そのまま note に貼れる形
├── images/                 実際に操作して撮った画面
└── README.md               入稿手順・画像の対応表・数字の出どころ・取材メモ
```

この仕事でいちばん外してはいけないのは、次の三つ。

第一に、書いたことが本当であること。だから撮影を先に済ませる。

第二に、人が書いた文章に読めること。作者本人が自分の作ったものを紹介する連載なので、
機械が並べたような文章だと、書き手ごと信用されなくなる。
記号や太字を禁じているのはその一点のためで、装飾の趣味の問題ではない。
ルールの全文は `references/style.md` にある。

第三に、書き手の記事になっていること。**書く前に本人から話を聞く。**
機能の説明はコードを読めば書けるが、「なぜその作りにしたのか」
「何をあえて作らなかったのか」は本人からしか出てこない。
そこが無い記事は、事実が正しくても、誰が書いても同じものになる。
聞きかたは `references/interview.md` にある。

## 書いた記事がどこへ行くか

`docs/note/` に置いた記事は、書き手が note に貼るだけのものではない。
三つの仕組みが、この同じファイルを毎日読んでいる。

一つ目は note。書き手が手で貼る。画像も手で上げる。

二つ目は `giga-school.com/apps/<slug>/` の紹介ページ。旗艦リポジトリ
`GIGAyama/GIGAyama.github.io` の GitHub Actions が、毎朝6時17分に各アプリの
`docs/note/*-note-article.md` を GitHub API で取ってきて、HTML に組み直している
（`tools/build-articles.mjs`）。記事は書きかえられない。見出しと画像の位置が
そのまま出る。見出しには `s-1` `s-3` の id が振られ、目次と、記事の中を探せる
検索の索引（節ごとに254件）がそこから作られる。

三つ目は投稿ランチャー（`GIGAyama/XXX_automatic`）。記事を note に貼れる形の
平文と画像の並びに分けて渡す。ついでに `config/note-style.json` を基準にした
体裁の検査をかけて、その結果を画面に出す。

つまり記事の書き方は、そのまま三つの仕組みの入力仕様になっている。
外しても人が読むぶんには気づけないので、`scripts/lint-article.mjs` が代わりに見る。

### 機械が頼っているところ

- **ファイル名に `note-article` を入れる。** これで記事だと判別している
- **`docs/note/` に記事以外の Markdown を置かない。** README.md 以外は
  2本目の記事として拾われる
- **画像は `images/01-home.png` の相対指定で、1行に1枚、行頭から。**
  文中に混ぜた画像は拾われない。外部のアドレスの画像は渡せない
- **1枚目の画像が SNS のカード画像になる。** ホーム画面など、そのアプリらしい絵にする
- **alt を空にしない。** 紹介ページの説明と読み上げに使われる
- **キャプションは画像の直後に1段落、60字まで。** 120字を超えると
  キャプションと見分けられず、同じ文が二度出る
- **最初の一段落が検索結果とSNSの説明文になる。** 110字で切られる
- **本文が1,200字未満だと取りこまれない。** 画像は60枚まで
- **ハッシュタグは記事のいちばん最後。** その下に段落があると拾われない。
  この節は note のためのもので、紹介ページには出ない（組み立てのときに落としている）
- **見出しの言葉を変えない。** 外から `#s-3` でリンクされている

### 記事に書いていないことは、サイトにも出ない

サイトの一覧には「アカウント不要」「記録は端末の中だけ」「対象学年」が
チップとして出るが、これは記事に書いてある事実からしか作らない。
推測で付けると、学校が誤った前提で導入を決めることになるため。
だから導入手順の節に、アカウントの要否と記録の残り先を、その言葉で書く。

### 画像が本当に読めるかを確かめる

紹介ページは、画像をアプリのサブドメインから読む。ただし Vite で `dist/` だけを
配っているリポジトリは `docs/note/images/` が配信物に入らない。いま31本のうち11本が
これに当たり、`raw.githubusercontent.com` に切り替わったうえで、SNS のカード画像が
サイト共通の絵に落ちている。

納品前に、1枚目の画像の URL をたたいて確かめる。

```bash
# ルートに CNAME があるリポジトリ
curl -sI https://<slug>.giga-school.com/docs/note/images/01-home.png | head -1
# docs/CNAME があるリポジトリ
curl -sI https://<slug>.giga-school.com/note/images/01-home.png | head -1
```

届かないなら、README にそう書く。1枚目だけを配信物（`public/` など）に足せば、
数百KBでカード画像が戻る。

## 途中から始めるとき

すでに記事と画像がある回を、片方だけやり直すこともできる。
0から6まで通す必要はないが、飛ばしていいものと、飛ばすと壊れるものがある。

**先に確かめること。** その記事がもう note に公開されているかどうか。
公開済みなら、本文を大きく書き換えると note と紹介ページの中身がずれる。
`giga-school.com/apps/<slug>/` は毎朝コミットから組み直されるが、
note は書き手が手で貼ったまま止まっている。
書き換えるなら、note 側も貼り直してもらう前提で進める。
その手間に見合わないなら、直すのは lint の ✗ だけにとどめる。

### 画面だけ撮り直す

アプリを直した、UI が変わった、壊れていた機能が動くようになった、というとき。

**ファイル名を変えない。** 本文の参照が切れる。番号の意味も保つ。
`--out docs/note/images` に同じ名前で上書きすれば、記事は直さなくて済む。

前回の `report.json` が残っていれば、`capture.mjs` が撮り比べて、
どの画面が変わったかを最後に出す。**変わった画面については本文を読み直す。**
画面が変わったのに書きぶりが前のまま、という食いちがいが、いちばん起きやすい。

1枚目を差し替えると SNS のカード画像も変わる。
枚数を減らしたときは、記事から参照が切れていないかを lint が拾う。

飛ばしていいのは取材と執筆。飛ばしてはいけないのは、撮り比べの読み合わせ。

### 記事だけ書き直す

文体を今の基準に合わせたい、内容を厚くしたい、というとき。

**画像が古びていないかを先に見る。** アプリが更新されてから撮り直していないと、
本文だけ新しくなって、写っているものと食いちがう。
lint がアプリ側と画像側の最終コミットを比べて、30日以上開いていれば警告する。
警告が出たら、書き直す前に撮り直す。

**取材はここでこそ要る。** 書き直しの目的はたいてい「機能の説明で終わっている」
ことの解消なので、足りていないのは事実ではなく、書き手の考えのほう。
`references/interview.md` を読んで、作らなかったものから聞く。

飛ばしていいのは撮影。飛ばしてはいけないのは取材。

### 画面を足すだけ

新しい機能ができたとき。撮って、本文に一段落と画像を足す。
追加した画像が末尾に並ぶと流れが崩れるので、番号を振り直すか、
`12b-` のような名前で間に入れる。

### 古い記事を今の基準に通す

31本ある既存の記事を手入れするとき。全面的に書き直さない。

lint をかけて、`✗` だけ直す。`⚠` は公開済みの記事なら基本そのままでいい。
体裁を整えるために本文の中身を動かすと、note との差が広がるだけで、
読み手にとっては何も良くならない。

## 進めかた

### 0. 先に三つだけ聞く

ここでの目的は、読む場所と撮る場面の狙いを決めること。長く聞かない。

- 連載番号。推測で埋めない。聞けないまま進むときは `#◯` のままにして、納品時に伝える
- このアプリを作ろうと思ったきっかけ。できれば、その日の場面
- いちばん届けたい先生はどんな人か

本番の取材は撮影のあと。理由は `references/interview.md` に書いてある。

前作の紹介記事が手に入るなら出してもらう。文体を合わせる材料になるし、
前作があれば「前作との差」が記事の推進力になる。

手本は `GIGAyama/Qalc` の `docs/note/qalc-note-article.md`。
本文7,590字、画面21点。迷ったらこれを見る。

### 1. アプリを読み解く

`README.md`、`MANUAL.md`（先生向けの手引きがあれば）、`package.json`、
`src/` の主要ファイルを読む。押さえるのは次のあたり。

- 何ができるアプリか。目玉はどれか
- 先生が知りたい制約。アカウントの要否、記録の残り先、
  校内フィルタリングで許可が必要なホスト名、オフラインで動くか、共用端末での注意
- 記事に書く数字。コース数、問題数、種類の数、上限値

フィルタリングのアドレスは、**いま配信に使っているホスト名**を書く。
アプリは `<slug>.giga-school.com` に移っているので、前の記事から写すと
古いアドレスのまま出る。`CNAME` を見て確かめる。

数字は必ず実測かコードで裏を取る。README は古くなっていることがある。
Qalc の回は README が「約11,800問」だったが、アプリのドリル一覧を数えたら 12,796 問だった。
数えられるものは、アプリを開いて数える。

裏を取った出どころは、あとで `docs/note/README.md` に一覧で残す。

### 2. 画面を撮る

**撮影を先に済ませる。** 撮っている最中に「実際はこう動く」「この機能は壊れている」が分かる。
先に文章を書くと、手もとの資料から想像で書いてしまい、事実と食いちがう。

先に `references/screenshots.md` を読む。踏んだ落とし穴が全部書いてある。

```bash
npm i --no-save playwright peer                             # 別々に入れると片方が消える
npm run build
node <skill>/scripts/serve.mjs dist 4180 /<リポジトリ名>/     # 別ターミナル、または背景で
node <skill>/scripts/capture.mjs .tmp-shots/shots.mjs \
  --base http://127.0.0.1:4180/<リポジトリ名>/ --out docs/note/images
```

`shots.mjs` は自分で書く。1台ぶんのブラウザを開いて、文字でボタンを押して、撮るだけ。

```js
export const viewport = { width: 390, height: 940 };

export default async ({ open, log }) => {
  const p = await open('main');
  await p.shot('01-home');
  log(await p.buttons());                              // 次に何を押せるか分からないときはこれ

  await p.clickTo('スコアアタック', '学年をえらぶ');    // 押して、画面が変わるまで見届ける
  await p.shot('02-select', { expect: '3年' });        // その文字が無ければ撮らずに止まる
};
```

`click` は押せなければ例外で止まり、そのとき押せるものの一覧を出す。
`shot` は画面が止まるまで待ち、直前と同じ絵なら警告する。
走り終えたら出力の最後のまとめを必ず読む。警告が出た画像は目で確かめる。

撮る枚数は 20枚前後。手本は21点で、31本の平均は22点。
ホーム、設定、動いているところ、結果、目玉の機能、先生向けの設定画面。

このうち6枚は、トップページのカードで順に切り替わるサムネイルにも使われる。
640×400 の 16:10 に切って使うので、**操作の流れが端から端まで伝わる6枚**が、
余白の少ない構図で撮れているとよい。候補は納品の README に挙げる。

撮影用のシナリオはリポジトリの中に置くことになる（`node_modules` の解決の都合）。
`.tmp-shots/` のような分かる名前にして、納品前に必ず消す。

最後の1回は `--strict` を付けて走らせる。画面のエラーが1件でもあれば異常終了する。

#### 撮っているあいだに、壊れている機能を見つけたら

記事より先にそれを報告する。動かない機能を紹介する記事を出すわけにいかない。
直せるなら直し、記事とは別のコミットに分けて、
「公開の前にこの修正を反映してください」と伝える。

撮影は、いちばん丁寧な受け入れテストでもある。そのつもりで踏む。

### 3. 話を聞く

**`references/interview.md` を読んでから聞く。**

アプリを読んで、実際に操作して、壊れているところまで踏んだあとなので、
ここでは具体的なことだけを聞ける。README に書いてあることは聞かない。

一度に一問か二問。選択肢は出さない。書き手の言葉が要る。
返ってきた答えを受けて、次の質問を決める。

とくに外せないのが二つ。作ろうと思った日の場面と、
作ろうとしてやめた機能。この二つが記事の背骨と、いちばん強い一段落になる。

書き手が忙しくて答えられないときは、そこを空けずに、コードとコミット履歴で
裏の取れる事実だけで埋める。理由は書かない。そのうえで、どの段落に何を足せば
強くなるかを README に一覧にして、あとから一段落だけ差し替えられる形にする。

聞き終えたら、聞き取った内容を短くまとめて書き手に見せ、
食いちがいがないか確かめてから書きはじめる。
取材メモは `docs/note/README.md` の中に残す。別ファイルにすると、
2本目の記事として自動で拾われる。

### 4. 記事を書く

`references/style.md` を読んでから書く。厳守ルールの散文の正本はあのファイルだけで、
ここには写しを置かない。二か所にあると、いつのまにか食いちがう。

書きかたとして、一度で仕上げようとしない。二回に分ける。

書く前に、この記事で言うことを一文に決める。取材で出た話のうち、
その一文に乗らないものは、面白くても落とす。全部入れると何も残らない。

一回目は、事実を全部そろえて通しで書く。撮った画像と `report.json` と取材メモを見ながら、
どの画面が何を見せているのかを本文に対応づける。ここでは文章の調子を気にしない。

二回目は、AIらしさを削るためだけに読み直す。見るのはこの4つ。

- 記号や太字で処理してしまったところ。文章に開く
- 中身のない言葉。「重要」「効率的」「一般的に」は、何がどうなるかに書きかえる
- 同じ長さ、同じ型の文が続いているところ。切るか、つなぐか、順番を変える
- 言い直しているだけの段落。消す

そのうえで、取材メモと突き合わせる。資料にも取材にも出どころが無い一文は消す。
書き手の言葉を、どこか一つはそのまま残す。

### 5. 機械で確かめる

```bash
node <skill>/scripts/lint-article.mjs docs/note/<app>-note-article.md
# 投稿ランチャーと同じ基準で見るとき
node <skill>/scripts/lint-article.mjs docs/note/<app>-note-article.md \
  --style ../XXX_automatic/config/note-style.json
```

`✗` は直す。`⚠` は見て判断する。`ℹ` は目安で、外れていても構わない。
警告を消すために文章を痩せさせない。判断した跡は納品の README に書く。

`--style` を渡すと、投稿ランチャーが当てているのと同じ基準になる。
渡さないときは、その写しを内蔵で使う。いまは両方とも 7,000〜12,000字。
片方だけ直すと、書き手が二つの検査から違うことを言われる。

### 6. 納品する

`docs/note/README.md` に、書き手が次に何をすればいいかを書く。

- note に貼る手順。タイトル行、画像の手動アップロード、キャプション欄、ハッシュタグ欄
- 貼るまえに直すところ（連載番号など）
- 取材メモ。聞いた問いと答え
- 差し替え待ちのところ。聞けなかったぶんは、事実だけで書いたうえで、
  どの段落に何を足すと強くなるかを一覧にする。記事の中に印は残さない
- 画像の一覧。ファイル名、何の画面か、本文のどこで使うか。`report.json` を見て書く
- サムネイル候補の6枚
- 1枚目の画像がサブドメインから読めるかを確かめた結果
- 記事に書いた数字の出どころ
- lint の警告のうち、あえて残したものとその理由
- 撮り直すときの手順

記事と修正は別のコミットに分ける。書き手が修正だけ先に出せるようにするため。
撮影のために一時的に当てた変更（接続先の差しかえ、CSP、`/etc/hosts`）が
差分に残っていないか、`git status` と `git diff` で必ず確かめる。
`.tmp-shots/` を消したかも、ここで見る。

記事を push した翌朝には紹介ページが自動で建つ。その日に一度、
`https://giga-school.com/apps/<slug>/` を開いて、画像が出ているかを見る。

## 手を出さないこと

- 教室での出来事を実体験として書かない。これは作者の実践記録ではないので、
  「使ってみたら子どもたちが〜」と書くと嘘になる。「こうなればいいと思って作った」まで
- 効果を言い切らない。「いちばん盛り上がる時間になる」ではなく「〜だと思います」
- 裏の取れていない数字を書かない。数えられるものは数える
- 元の資料にない事例や固有名詞を足さない
- 取材で聞いていない考えを、書き手の考えとして書かない。
  無理に引き出した話も同じで、本人が読んで「そんなに思っていない」と感じる一文が
  一つでもあると、その記事は本人の名前で出せなくなる
- 収益化の導線を入れない。地方公務員法38条の確認が済むまでは出さない決まりになっている
- スクリーンショットを加工・合成しない。実際に操作して撮ったものだけを使う
