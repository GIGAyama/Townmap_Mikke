# 開発記録の記事を作る

このセッションでやった開発を、記事 1 本にして `docs/devlog/` に納品する。

```
docs/devlog/
└── <日付>-<短い名前>.md    例: 2026-08-24-backlink.md
```

## 読み手

**生成 AI でアプリを作っている人**と、**このアプリを使ってどう作ったか知りたい人**。

note の紹介記事（`note-article` スキル）は先生に向けて書く。こちらは違う。
`Service Worker` を「裏で動く仕組み」と言い換えたら、この読み手には**役に立たない**。
専門語はそのまま使う。

## 外してはいけない三つ

**第一に、プロンプトがそのまま使えること。** ここがこの記事のいちばんの価値。
読んだ人が自分のリポジトリで同じことをできる形で残す。書き方は `references/prompts.md`。

**第二に、行き止まりを隠さないこと。** うまくいった話だけ並べても読み物にならないし、
役にも立たない。何を試して駄目だったか、なぜ駄目だったかが、次に同じことをする人を助ける。

**第三に、新しく覚えたことが書いてあること。** その開発で何ができるようになったのか。
これが無い記事は、作業報告であって記録ではない。

## 会話の書き起こしではない

⚠️ **セッションのやりとりをそのまま貼らない。** 読み物にならない。

起きたことを時系列で洗い出したうえで、**筋を立てて書き直す**。
実際には行きつ戻りつしたことでも、記事では「こう考えた、こうなった、だからこうした」の
順に組み直してよい。ただし**うまくいったように見せるための組み替えはしない**。

## 書いた記事がどこへ行くか

`docs/devlog/` に置いた記事は、旗艦リポジトリ `GIGAyama/GIGAyama.github.io` の
GitHub Actions が毎朝 6:17 に GitHub API で取ってきて、
`giga-school.com/devlog/<アプリ>/<記事>/` に組み直す（`tools/build-devlog.mjs`）。

`docs/note/*-note-article.md` が `/apps/<slug>/` になるのと同じ仕組み。

### 機械が頼っているところ

- **`docs/devlog/` に置く。** 場所で判別している
- **front matter が要る**（下記）。無いものは拾われない
- **`published: true` にするまで出ない。** 既定は `false`
- 見出しには `s-1` `s-3` の id が振られ、目次がそこから作られる

### front matter

```markdown
---
app: typa
title: 「せってい」のどこに置くか、3 回変えた
date: 2026-08-24
pr: 38
published: false
---
```

| 鍵 | 要るか | 中身 |
|---|---|---|
| `app` | 必須 | `data/apps.json` の `slug`。実在しないと組み立てで落ちる。サイト本体（giga-school.com）への変更なら `site` |
| `title` | 必須 | 記事の題。連載番号は付けない |
| `date` | 必須 | `YYYY-MM-DD` |
| `pr` | 任意 | PR 番号。あれば日付と差分の規模が自動で添えられる |
| `published` | 必須 | **`false` で納品する。** 公開は本人が決める |

`app: site` は、このサイト自身への変更のための枠。トップページ、紹介ページの
組み立て、検査の仕組み。これらは `data/apps.json` に載っていないので、
適当なアプリの slug を借りると、そのアプリの「つくり方」に無関係な記録が混ざる。

⚠️ **`published: true` にして納品しない。** プロンプトには生の事情が混ざる。
本人が目で見て決めるための仕組みなので、書いた側が先に立てない。

## 進めかた

### 0. このセッションで何をしたかを洗い出す

記事を書き始める前に、時系列で並べる。まだ文章にしない。

- 出したプロンプト（効いたもの、効かなかったもの、両方）
- 行き止まり。何を試して、どう駄目だったか
- 方針を変えたところと、その理由
- 測ったこと、数えたこと
- 直した結果（PR 番号、差分の規模）

⚠️ **測った数字は必ず拾う。** 「速くなった」ではなく「652ms から 431ms」。
この連載は数字で書く。

### 1. 本人に三つ聞く

会話の流れで拾えていれば聞き直さない。**聞けたことだけ書く。**

- **いちばん詰まったところはどこでしたか**
  → 「うまくいかなかったこと」の山になる
- **これをやって、新しくできるようになったことはありますか**
  → 「新しく知ったこと」。ここが本人からしか出てこない
- **次に同じことをする人に、先に言っておきたいことはありますか**
  → 最後の節

聞けないときは、その節を**空のまま出さない**。書ける節だけで記事にする。
`references/structure.md` の「話を聞けないとき」を見る。

### 2. プロンプトを他人が使える形に直す

`references/prompts.md` の手順どおりに。ここが記事の価値を決める。

### 3. 記事を書く

`references/structure.md` の節構成。文体は `references/style.md`。

### 4. 機械で確かめる

```
node .claude/skills/devlog-article/scripts/lint-devlog.mjs docs/devlog/<記事>.md
```

`✗` は直す。`⚠` は見て判断する。`ℹ` は目安。`✗` が 1 件でもあると終了コードが 1 になる。

⚠️ **`note-article` の `lint-article.mjs` は使えない。** はじめは `--style` で設定を
差し替えて共用するつもりだったが、試したところ 6 か所が設定では外せなかった。
ファイル名が `*-note-article.md` であること、1 行目が `# タイトル` であること
（front matter の `---` を水平線として弾く）、ハッシュタグが要ること、
1,200 字の下限、置き場所が `docs/note/` であること。
どれも紹介記事の形に埋めこまれている。

`lint-devlog.mjs` は、そちらの文体のルールと囲み（```）の扱いだけを借りた別物。

### 5. 納品する

`docs/devlog/<日付>-<短い名前>.md` に置く。`published: false` のまま。

本人に伝えること。

- 記事の置き場所
- **公開するには front matter の `published` を `true` にすること**
- プロンプトに残っている固有名詞があれば、その箇所

## 手を出さないこと

- **`published: true` にしない。** 公開は本人が決める
- **アプリのコードを直さない。** 記事を書く仕事であって、開発の続きではない
- **セッションのリンク（`claude.ai/code/session_…`）を書かない。**
  本人しか開けない。コミット本文には 67 件あるので、引用で紛れこみやすい
- **数字を作らない。** 測っていないものは書かない
- **note の紹介記事を直さない。** あれは `note-article` スキルの仕事
