# 使い方マニュアルを作る

リポジトリにある学校向けWebアプリについて、**そのアプリを初めて開いた人が、
ほかに何も見ずに最後まで使えるようになる**マニュアルを、実画面の写真つきで作る。

納品物はこの 2 つ。

```
docs/manual/
├── manual.md   本文。名前は決め打ち（後述）
└── images/     マニュアルのために撮った画面。01- からの連番
```

## 紹介記事とどう違うのか

同じアプリについて 2 つの文書がある。取り違えると、どちらも役に立たなくなる。

| | 紹介記事（note-article） | マニュアル（このスキル） |
| --- | --- | --- |
| 読み手 | まだ使っていない**先生** | いま画面を開いている**使う人** |
| 知りたいこと | 教室でどう効くのか。入れる値打ちがあるか | この画面のこのボタンは何なのか |
| 書くこと | なぜ作ったか。何をあえて作らなかったか | 全部の機能と、その出しかた |
| 読み手の気分 | 面白そうなら読む | 困っている。早く答えが欲しい |
| 文体 | 語りかける散文 | 番号つきの手順。短く言い切る |

⚠️ **紹介記事の「使い方のガイド」の節を写して済ませない。** あれは記事の中で
話の流れを保つために絞ってある。マニュアルは絞らない。**全部の機能を書く。**

読み手はアプリごとに違う。子どもが直接使うアプリなら子どもに向けて書き、
先生だけが使うアプリなら先生に向けて書く。**どちらに向けるかを最初に決める。**
決め方は `references/format.md` に書いてある。

## 書いたマニュアルがどこへ行くか

`docs/manual/manual.md` は、リポジトリの中だけのものではない。

旗艦リポジトリ `GIGAyama/GIGAyama.github.io` の GitHub Actions が、毎朝
各アプリの `docs/manual/manual.md` を GitHub API で取ってきて、
`giga-school.com/apps/<slug>/manual/` として組み直している
（`tools/build-manuals.mjs`）。見出しには `s-1` `s-3` の id が振られ、
そこから目次と、印刷用の体裁と、サイトの検索の索引が作られる。

そしてアプリの画面からは、正本の部品 `giga-app-links.js` が
このページへの「つかいかた」のリンクを出している。
**つまり、ここに書いたものが、アプリの中の「つかいかた」の中身になる。**

### 機械が頼っているところ

- **ファイル名は `docs/manual/manual.md`。** 決め打ちで探している。
  `docs/manual/` があるのにこの名前が無いと、組み立ては警告を出して飛ばす
- **画像は `images/01-home.png` の相対指定で、1 行に 1 枚、行頭から。**
  文中に混ぜた画像は拾われない。外部のアドレスは渡せない
- **`#` は 1 本だけ。** それがページの題になる（本文には出ない）
- **`##` の並びと言葉を変えない。** 目次と索引がこの並びを前提にしている
- **番号つき手順の途中に画像を置かない。** 画像の行でリストが切れて、
  番号が 1 に戻る。画面写真は手順の前か、手順を終えてから
- **キャプションは画像の直後に 1 段落、120 字まで。** 超えると本文の段落として
  二度出る
- **「学校で使うときは」の節を自分で書かない。** 許可するアドレス・アカウントの
  要否・記録の置き場は `data/apps.json` から機械が足す。手で書くと
  `giga-school.com/filtering/` と食い違い、「許可申請は通ったのに開かない」
  という、いちばん困る形になる
- **表・水平線・太字・絵文字を使わない。** 組み立てが扱わない

`scripts/lint-manual.mjs` が、これらを機械で見る。

## 進めかた

### 1. 読み手を決めて、既にあるものを探す

`MANUAL.md`、`README.md` の使い方の節、`docs/` の中の手順書。
**すでに書いてあるものを捨てない。** 週案エディタには 318 行の `MANUAL.md` が
あった。書き直すのではなく、この形へ移す。

### 2. 全機能を数える

コードから機能の一覧を作る。画面のタブ、メニュー、ボタン、右クリック、
設定の項目。**ここで数えたものが、そのまま「できること」の節の数になる。**
数えずに書きはじめると、書きやすい機能だけが並んだマニュアルになる。

### 3. 実ブラウザで、数えた全部をさわる

撮影の土台は **note-article スキルの `scripts/capture.mjs` をそのまま使う**。

```
node .claude/skills/note-article/scripts/capture.mjs shots.mjs --base <URL> --out docs/manual/images --strict
```

⚠️ **撮影の土台を作らない。** capture.mjs は `tools/distribution.json` の
`skills.required` で 42 本すべてに配られている。2 つ持つと必ずずれる。
押せなかったら止まる、画面が変わらなければ警告を出す、という仕掛けが
向こうに入っているので、それに乗る。

マニュアル用の撮り方（紹介記事用とどう違うか）は `references/screenshots.md`。

### 4. 書く

`references/format.md` の見出しの並びのとおりに書く。
**さわっていないものを書かない。** 押していないボタンの説明を
コードから書くと、画面の言葉と食い違ったまま気づけない。

### 5. 検査

```
node .claude/skills/giga-manual/scripts/lint-manual.mjs docs/manual/manual.md
```

そのリポジトリに在る検査も通す（`package.json` の `scripts` を先に見る。
無いものを走らせて ENOENT で止まるのは「検査に通っていない」であって
「検査が無い」ではない）。
